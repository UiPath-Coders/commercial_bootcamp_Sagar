# POMatch_Reference — Lab 3 reference solution (Match PO and Check Approval)

Facilitator reference for **Lab 3 — UiPath Functions (Python)** of the Commercial Bootcamp
(Office of the CFO, Invoice-to-Pay). It is the project a participant is expected to end up with
after following `bootcamp-site/src/data/labs/lab3.ts`, built with the `uipath-functions` skill and
named with the suffix `Reference` where a participant has their first name.

Canonical spec: `bootcamp-site/docs/commercial-process.md`. API contract: `../../samplepolookup.md`.
Everything here is synthetic. There are no credentials anywhere in this folder.

### The four functions

The lab asks for four entry points. They share one implementation of the PO rules and one set of Data
Fabric helpers, so nothing is written twice:

| Entry point | What it is for | Touches |
|---|---|---|
| `po_lookup` | The pure rule function. Easy to test on a laptop. | The ERP only |
| `process_invoice` | Match one invoice record. This is what the Lab 10 Maestro process calls. | Reads and writes one record |
| `process_invoice_queue` | The standalone Lab 3 runner: drain the queue, one `process_invoice` per transaction. | Queue + records |
| `get_invoice_status` | Let the Lab 10 wait loop see the reviewer decision from the Lab 6 app. | Reads one record, never writes |

**`po_lookup(vendor_name, po_number, invoice_total, currency)`** — pure, no UiPath SDK. Sends
`POST {ERP_PO_LOOKUP_URL}` with `{vendorName, poNumber, invoiceTotal, currency}` and applies:

```
po_matched        = po.found AND po.vendorActive AND |invoice_total - po.openAmount| <= 2% * po.openAmount
approval_required = NOT po_matched OR invoice_total > 10000
```

Output: `po_matched`, `approval_required`, `open_amount`, `match_reason`
(`MATCHED | PO_NOT_FOUND | VENDOR_INACTIVE | OUTSIDE_TOLERANCE`), `error_type`, `error_message`.
It never guesses: a non-200 status (`ERP_HTTP_ERROR`), a connection/timeout failure (`ERP_UNREACHABLE`),
a non-JSON body or a body without a well-typed `po` object (`ERP_MALFORMED_RESPONSE`), or a blank PO
number (`INVALID_INPUT`) populates the error fields and returns `po_matched=false, approval_required=true`
(fail safe). Callers must treat a non-empty `error_type` as "no answer", which is exactly what the other
entry points do.

**`process_invoice(record_id, entity_name="AP_Invoice_Reference")`** — one record.

1. Finds the entity (and, when the tenant returns the schema, checks that `VendorName`, `PONumber`,
   `TotalAmount`, `Currency`, `POMatched`, `ApprovalNeeded` exist with exactly those names).
2. Reads exactly that record, runs the shared `po_lookup` code with its VendorName, PONumber, TotalAmount
   and Currency.
3. Writes `POMatched` and `ApprovalNeeded` back to the same record. If the record already holds those
   values the write is skipped, so running the same record twice is safe and gives the same answer.

Output: `record_id`, `po_matched`, `approval_required`, `open_amount`, `match_reason`, `error_type`,
`error_message`. Problems are returned, never raised: `INVALID_INPUT` (blank id), `ENTITY_RESOLUTION_FAILED`,
`RECORD_NOT_FOUND`, `RECORD_READ_FAILED`, `INVALID_RECORD` (empty or non-numeric TotalAmount), any
`po_lookup` error type, `RECORD_UPDATE_FAILED`, `ERP_AUTH_CONFIGURATION_FAILED`. On any error nothing is
written to the record.

**`process_invoice_queue(queue_name, folder_path, entity_name, entity_id, erp_api_token_asset_name, max_items)`**
— the queue wrapper. It holds no business rules of its own.

1. Reads the optional token asset and resolves the entity once. If either fails the run stops with
   `ERP_AUTH_CONFIGURATION_FAILED` or `ENTITY_RESOLUTION_FAILED` before touching the queue.
2. Repeats up to `max_items` times: *Start Transaction* on the queue (`no_robot=True` unless the job sets
   `UIPATH_ROBOT_KEY`). An empty queue answers 204 with no body; the SDK turns that into
   `json.JSONDecodeError`, which is the normal "queue is empty" signal. Any other exception ends the run
   with `QUEUE_ERROR`.
3. Each transaction's `Reference` is the record Id. It is handed to `process_invoice`. If that returns no
   error the transaction is marked **Successful** (with `POMatched`, `ApprovalNeeded`, `MatchReason` as
   output); otherwise it is marked **Failed** with a `BusinessException` naming the record, the problem is
   added to `errors`, and the loop moves on.

Output: `processed`, `matched`, `approval_required`, `failed`, `errors[]`, plus `error_type` /
`error_message` when the run itself could not proceed.

**`get_invoice_status(record_id, entity_name="AP_Invoice_Reference")`** — read-only. Returns `record_id`,
`invoice_lifecycle_state`, `approval_needed`, `posted_to_erp`, `reviewed_by`, `reviewed_at`, `found`,
`error_type`, `error_message`. It performs no write of any kind (the tests fail if it tries). Day 1
entities do not have `InvoiceLifecycleState`, `ReviewedBy` or `ReviewedAt` yet; those come back as empty
strings rather than an error. When `ApprovalNeeded` is not set yet, `approval_needed` is `true` (the safe
assumption: a person still has to look); an unset `PostedToERP` is `false`. A record that does not exist
gives `found=false` and `RECORD_NOT_FOUND`.

Logging: only record Ids and outcomes. Vendor names, amounts, tax IDs and bank details are never logged.

### Things the cloud robot taught us

These were found by running the earlier version on the serverless robot. The code and tests now cover them.

- **Queue items are completed by their numeric `Id`, not their `Key`.** A transaction has both a GUID `Key`
  and a numeric `Id`. Orchestrator's *Set Transaction Result* call is addressed by the numeric `Id`; sending
  the `Key` returns 404 and the item stays *In Progress* forever. The `Key` is now only used in messages.
- **"Empty body" is success when completing a transaction.** Orchestrator answers 200 with nothing in the
  body. The SDK still tries to read JSON from it and raises `Expecting value: line 1 column 1`. That
  specific error is treated as success. Real HTTP errors (4xx/5xx) are still reported.
- **Field names change case between tools.** The entity schema says `PONumber`, `POMatched`,
  `PostedToERP`. The uip df CLI prints `PoNumber`, `PoMatched`, `GlAccount` and omits null fields; the
  Python SDK returns the schema names (`PONumber`, `POMatched`, `PostedToERP`). Reads ignore case; writes
  always use the schema names.

### Configuring the ERP address: `ERP_PO_LOOKUP_URL`

`ERP_PO_LOOKUP_URL` holds the **complete** PO-lookup address, and the code uses it exactly as given.

- Local default: `http://localhost:8080/api/po-lookup`.
- Hosted: the signed URL from the bootcamp site, which ends in `?access_token=...`. Paste it whole. Nothing is
  added to it, and the token is replaced with `***` in every log line and error message.
- Older setups that set `ERP_API_URL` (a base address such as `http://localhost:8080`) still work: when
  `ERP_PO_LOOKUP_URL` is not set, `/api/po-lookup` is appended to `ERP_API_URL`.

## Run it locally

Prerequisites: `uv`, the `uip` CLI (1.200.x), and the mock ERP running
(`node server.mjs` in `commercial_bootcamp_lab_assets/mock-erp`, default `http://localhost:8080`).

```bash
cd commercial_bootcamp_lab_assets/lab3-api/reference/POMatch_Reference

uv sync                                  # creates .venv with uipath 2.14.x, httpx, pydantic, pytest
source .venv/bin/activate                # Windows PowerShell: .venv\Scripts\Activate.ps1
python -m pytest -q                      # 107 tests; the live ones FAIL loudly if the ERP is down
POMATCH_SKIP_LIVE=1 uv run pytest -q     # skip the live-ERP tests (offline)

uip function init                        # uses this project's uipath executable; regenerate derived files
uip function run po_lookup --input '{"vendor_name":"Vertex Analytics Corp.","po_number":"PO-2026-0405","invoice_total":22700,"currency":"USD"}'
uip function run po_lookup --input '{"vendor_name":"Vertex Analytics Corp.","po_number":"PO-0000-9999","invoice_total":22700,"currency":"USD"}'
uip function run process_invoice --input '{"record_id":"<RECORD_ID>"}'       # needs uip login + the Lab 2 entity
uip function run get_invoice_status --input '{"record_id":"<RECORD_ID>"}'    # read-only
uip function pack                        # .uipath/POMatch_Reference.0.1.0.nupkg (local only)
```

For local work, keep the included server running; the default `ERP_PO_LOOKUP_URL` already points at it.
Set `ERP_PO_LOOKUP_URL` to the complete signed hosted URL only when a cloud runtime needs to reach the ERP.

### Renaming `Reference` to a participant's first name

Nothing in the code is hard-wired to `Reference`. Either set `BOOTCAMP_USER_NAME=<user_name>` (renames
`InvoiceQueue_*`, `APAutomation_*`, `AP_Invoice_*` in one go), set `INVOICE_QUEUE_NAME` /
`AP_FOLDER_PATH` / `AP_INVOICE_ENTITY_NAME` individually, or pass `queue_name` / `folder_path` /
`entity_name` as job input. The project name (`pyproject.toml` `name`, `project.uiproj` `Name`) is the
only place `POMatch_Reference` appears; rename it there and re-run `uip function init` for a participant copy.

## What was NOT verified offline (facilitator must check on the tenant)

`process_invoice`, `process_invoice_queue` and `get_invoice_status` are exercised only against an in-memory
fake of the SDK whose methods match the signatures in `uipath` 2.14.12 (`queues.create_transaction_item`, `queues.complete_transaction_item`,
`entities.retrieve_by_name`, `entities.retrieve`, `entities.get_record`, `entities.update_record`). Not proven
against a real tenant:

1. **Authentication and folder scope on the serverless robot** — that the job's execution context resolves
   `Agentic Bootcamp/APAutomation_<user_name>` (the default `folder_path` is this full path; the bare name
   `APAutomation_<user_name>` returns 400 "Folder does not exist or the user does not have access"). *Start Transaction* is sent with the robot association only when
   `UIPATH_ROBOT_KEY` is present (the SDK raises without it, so local runs pass `no_robot=True`); that the
   robot-associated variant is accepted on the serverless runtime is untested.
2. **`entities.retrieve_by_name` for a tenant-scoped entity** returns the schema (`fields`) — when it does
   not, the field-name check is skipped and the first `update_record` is where a wrong name would fail.
3. **`entities.update_record` with a partial body** (`POMatched`, `ApprovalNeeded` only) leaves the other
   fields untouched, and the two Boolean fields accept Python `True/False`.
4. **Empty-queue behaviour**: *Start Transaction* returning 204 surfaces from the SDK as a JSON decode
   `ValueError` (handled) rather than an HTTP error. (Completion by numeric `Id` and the empty 200 body on
   *Set Transaction Result* were observed on the serverless robot and are now handled; the fake reproduces both.)
5. The exact `ProcessingException` shape (`{"Type": "BusinessException", "Reason": ...}`) is accepted by
   *Set Transaction Status*.
6. Publish to the folder feed, process creation and the serverless job (lab steps 5-6).

One unintended live call happened during validation: `uip function run process_invoice_queue --input '{}'`
on this machine picked up an existing `uip login` session and made a single read-only
`GET .../datafabric_/api/Entity/AP_Invoice_Reference/metadata` against `customersuccessamer/Training`, which
returned 400 *Entity 'AP_Invoice_Reference' not found at tenant level* -> the function reported
`ENTITY_RESOLUTION_FAILED` and took no transactions. Nothing was created, written or published. It does
confirm the SDK auth and the entity-by-name endpoint work end to end; a participant with the entity from
Lab 2 in place would get past that step.
