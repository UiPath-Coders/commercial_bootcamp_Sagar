# Invoice_Approval_Agent_Reference — Lab 5 reference solution

Facilitator reference for **Lab 5 — Code-first Agent** (Commercial Bootcamp, Office of the CFO,
Invoice-to-Pay). It is the *Build Approval Package* step of the process: a LangGraph coded agent that
reads one `AP_Invoice_<user_name>` record from Data Fabric, runs the four deterministic gates before
any LLM reasoning, asks the LLM (through the UiPath LLM Gateway) for the approval narrative **only**
when the invoice is ready for approval, and writes six output fields back to the **same** record.

This is what a participant is expected to end up with under `lab5-coded-agent/agent/`. It was
scaffolded with `uip codedagent new` and `uip codedagent init` per the `uipath-agents` skill, and it
runs and passes its tests locally without a tenant. Everything in it is synthetic; there are no
credentials anywhere.

```
Input   {"recordId": "<AP_Invoice record Id>"}         (+ optional "entityName" override)
Graph   START -> load_record -> evaluate_gates -+-> write_narrative -> write_back -> END   gate 4
                                                +----------------------^                   gates 1-3
Output  record_id, invoice_reference, approval_evidence_state, missing_approval_fields,
        recommendation, invoice_lifecycle_state, agent_processed_at, narrative_generated
Writes  ApprovalEvidenceState, MissingApprovalFields, AgentRecommendation, ApprovalPackageJson,
        AgentProcessedAt, InvoiceLifecycleState   (nothing else - no Status field, no second entity)
```

## The four gates (from `bootcamp-site/docs/commercial-process.md`)

| # | Condition | `ApprovalEvidenceState` | `AgentRecommendation` = `InvoiceLifecycleState` | LLM |
|---|---|---|---|---|
| 1 | `POMatched == false` | `NOT_EVALUATED` | `HOLD_PO_MISMATCH` | no |
| 2 | `ApprovalNeeded == false` (explicit; unset counts as true) | `NOT_REQUIRED` | `AUTO_APPROVED` | no |
| 3 | any of `GLAccount`, `CostCenter`, `Approver`, `ReceiptReference` empty | `INCOMPLETE` | `NEEDS_AP_REVIEW` (+ `MissingApprovalFields`) | no |
| 4 | all checks pass | `COMPLETE` | `READY_FOR_APPROVAL` | **yes** — narrative inside `ApprovalPackageJson` |

The gates live in `approval_gates.py` as a pure function (`evaluate_gates(record) -> GateResult`) with
no I/O, so they are unit-tested directly against the lab dataset.

## Run the tests locally (no tenant, no login)

```bash
cd commercial_bootcamp_lab_assets/lab5-coded-agent/reference/Invoice_Approval_Agent_Reference
uv venv --python 3.13 .venv && source .venv/bin/activate     # Windows: .venv\Scripts\activate
uv sync                                                        # installs uipath-langchain, langgraph, pytest (uv.lock)
uip codedagent setup --force                                   # point the uip wrapper at this venv

.venv/bin/python -m pytest -q                                  # 70 passed
uip codedagent eval agent evaluations/eval-sets/smoke-test.json --no-report --workers 1   # 6 x 1.0
uip codedagent review .                                        # PASS, A+
```

Run the agent end-to-end **offline** against the lab seeds (Data Fabric replaced by the CSV, LLM

## Run against a real tenant (what the lab actually does)

1. `uip login --authority https://staging.uipath.com/identity_ --organization customersuccessamer --tenant Training`
2. `cp .env.example .env` and set `AP_INVOICE_ENTITY_NAME=AP_Invoice_<user_name>` (the tenant-scoped
   entity from Lab 2, already extended with the 14 Day 2 fields). Optionally set
   `AP_INVOICE_ENTITY_ID` to skip name resolution.
3. Check the model in `AP_INVOICE_LLM_MODEL` exists: `uip codedagent list-models`.
4. `uip codedagent run agent '{"recordId":"<CANONICAL_RECORD_ID>"}'` — then read the record back:
   `uip df records list <ENTITY_ID> --output json`.
5. For a live evaluation, regenerate `smoke-test.json`, delete the `mockingStrategy` blocks and replace
   each `recordId` with the Data Fabric Id of the imported AP-TRAIN record.
6. Deploy: `uip codedagent deploy --tenant`, then
   `uip or processes create --name Invoice_Approval_Agent_<user_name> --package-key Invoice_Approval_Agent_<user_name> --package-version <v> --folder-key <APAutomation key>`,
   then run it with `uip or jobs start <process-key> --folder-key <APAutomation key> --input-arguments '{"recordId":"<id>"}' --wait-for-completion`
   (bump `version` in `pyproject.toml` on redeploy). `deploy --folder` fails: it selects a folder feed
   (`Folder 'APAutomation_<user_name>' not found`).

## How the lab steps map to this project

| Lab 5 step | Where it lives here |

## Design notes facilitators should be able to explain

- **Gates before LLM, by construction.** `evaluate_gates` has no dependencies; the graph routes to
  `write_narrative` only when `fired_gate == 4`. Tests assert the call order `read -> llm -> write`
  for gate 4 and `read -> write` for gates 1–3.
- **One record, six fields.** `write_agent_outputs` raises if asked to write any field outside the six
  (so nobody sneaks in a `Status`). Reads and writes use the same `recordId`; the entity is resolved by
  name at tenant scope (no `folder_key`).
- **`MissingApprovalFields`** is a Text field, so it is written as a comma-separated list in the canonical
  order `GLAccount, CostCenter, Approver, ReceiptReference` (empty string when complete). The graph
  output keeps it as a JSON array.
- **`ApprovalPackageJson`** always holds the structured package (invoice, PO match, evidence, the gate
  trace, the decision). The `narrative` block is `null` for gates 1–3 and `{summary, risk_flags,
  confidence, source, model}` for gate 4. `source` is `llm` normally, `template` when the gateway is
  disabled or fails (the deterministic decision is still written; the reason is recorded).
- **`AgentProcessedAt`** is UTC ISO-8601 (`2026-09-07T00:44:13Z`), set on every run.
- **Missing `POMatched`** (Lab 3 never ran) is treated as `false` -> `HOLD_PO_MISMATCH`, never auto-approved.
- **Booleans from CSV imports** arrive as `"True"/"False"` text; the gates normalise them.
- **No module-level SDK/LLM clients**: `UiPath()` and `UiPathChat()` are created inside functions so
  `uip codedagent init` can import the module without credentials.

The bootcamp prompt and this reference both use `recordId` as the required input. The optional
`entityName` override is a local/reference convenience; participant projects normally read the entity name
from configuration. The generated `bindings.json` is empty because Data Fabric entities are accessed through
the SDK rather than fabricated as agent resources. The offline smoke evaluation mocks each record read;
live evaluation cases instead use the imported records' real Data Fabric IDs.

## Contract gap: this reference predates the Lab 5 prompt

The Lab 5 prompt asks for outputs `recordId`, `recommendation`, `invoiceLifecycleState`, `wasAlreadyPrepared`
and the error fields `errorType` / `errorMessage`, plus a retry guard that skips repeated LLM work. This
reference predates that contract:

- no retry guard (a rerun on a prepared record calls the LLM again);
- no `wasAlreadyPrepared`, `errorType` or `errorMessage` outputs;
- snake_case outputs (`invoice_lifecycle_state`) instead of the camelCase contract;
- an optional `entityName` input the prompt does not ask for;
- its pytest files import reference internals, so they are not a black-box gate test for your agent.

Use it for the gate logic, the Data Fabric read/write and the narrative call. Follow the prompt, not this
reference, for the input/output contract and the retry guard.
